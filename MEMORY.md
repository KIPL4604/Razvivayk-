## 7. Покер: реализованное поведение

**Heads-up No Limit Texas Hold’em, строго два места.** Стартовый стек по
1000 виртуальных фишек, малый/большой блайнд 10/20. Бот или второй проверенный
пользователь Telegram. Онлайн-комната создаётся одним игроком; второй вводит
шестизначный код. В браузере доступен настоящий серверный solo с отдельным
секретным токеном. Покупки, вывод и ставки реальными деньгами не реализованы.

Правила на сервере: префлоп/флоп/тёрн/ривер/вскрытие; очередность heads-up,
смена дилера, burn-карты, пас/чек/колл/рейз/олл-ин, минимальное повышение,
короткие олл-ины, возврат непокрытой части ставки, лучшая пятёрка из семи,
кикеры, младший стрит A–2–3–4–5 и делёж банка. Сумма рейза — полная ставка
на текущей улице, включая уже вложенные игроком фишки этой улицы.

Сервер перемешивает колоду через `secrets.SystemRandom`, выполняет правила и
возвращает отдельный вид для каждого игрока. До вскрытия видны только свои
карты. Пас не раскрывает руку соперника или победителя. Клиент не получает
колоду. Состояние сериализовано в SQLite, ходы версионированы, запись атомарна.

Бот учебный, с расчётом против случайной неизвестной руки и вероятностными
решениями; не объявлять его GTO-ботом. При оценке equity бот получает только
свои карты и общий борд. Подсказка также не читает реальную руку соперника.

Обучающая подсказка:

- Equity — оценка средней доли банка против случайной руки, включая ничьи.
- Монте-Карло: **400 симуляций** на подсказку.
- Порог колла: `C / (P + C)`.
- EV колла: `equity × (P + C) − C`.
- `C` — доступная цена колла; `P` — доступный банк до колла с исключением
  непокрытого избытка, который короткий стек выиграть не может.
- Текст объясняет сравнение колла и паса в рамках модели. Будущие ставки,
  диапазон соперника и fold equity не учитываются. Приближённый расчёт не
  гарантирует победы в отдельной раздаче.

После результата оба человека подтверждают следующую раздачу; бот готов
автоматически. Банкротство заканчивает матч. Выход в каталог сохраняет стол;
«Завершить стол» закрывает комнату для обоих. После последнего изменения
комната хранится **72 часа**. Есть очистка недоступного сохранения в интерфейсе.

Обновления — HTTP polling примерно раз в **1,5 секунды** на активном экране.
`MAX_ROOMS = 2000` ограничивает все ещё не истёкшие записи комнат, включая
закрытые. Это защитный лимит хранения, не доказанная пропускная способность.

Исправленные гонки и взаимодействия:

- Поздний poll не откатывает более новую версию комнаты.
- Подсказка показывается только для своей версии комнаты.
- Ответ создания комнаты сохраняет стол, но не возвращает пользователя за
  него после ухода в каталог.
- Успешный leave очищает сохранение даже после навигации.
- После 409 готовность `next` может повторяться только для той же завершённой
  раздачи, если действие ещё доступно. Ставки автоматически не повторяются.
- Сохраняются keyboard focus и позиция прокрутки при перерисовке.
- Длинные имена переносятся и не раздвигают стол.

## 10. Оценка платформы и дальнейшие предложения

Пользователь спросил о масштабировании и сообщил о планах полноценной игровой
платформы. Ассистент выполнил read-only анализ текущего кода; приложение при
этом не переписывалось. Вывод: существующие игры и Python API можно сохранить,
но платформенные возможности нужно выделить и развивать отдельно.

Подтверждённые ограничения текущего состояния:

1. Головоломки, шахматы и покер пока подключаются через отдельные прямые
   интеграции; общего контракта независимого игрового модуля ещё нет.
2. Общие лобби, matchmaking, универсальные приглашения, таймеры ходов и
   единые правила отключения для всех игр ещё не реализованы.
3. Покер — два игрока и polling; универсального WebSocket-слоя нет.
4. При 1000 одновременно активных покерных клиентах интервал 1,5 s даёт
   теоретически примерно до 667 GET/s только на опрос, ещё без ходов/подсказок.
   Это арифметика частоты, не измеренная вместимость сервера.
5. Лимит 2000 сохранённых комнат не означает проверенную работу 2000 комнат.
   Закрытые комнаты тоже учитываются до истечения TTL.
6. SQLite допускает одного писателя на файл. Бот считает ответ внутри
   транзакции записи покерного хода; при росте это вероятное узкое место.
7. Сервер головоломок проверяет пользователя, сессию и ограничения, но факт
   решения сообщает клиент. Перед соревновательными рейтингами, призами или
   ценной экономикой нужна проверка результатов, а не доверие клиентскому флагу.
8. Шахматные партии и статистика пока локальные, а не общие облачные.
9. Текущий локальный запуск зависит от работающего компьютера и временного
   HTTPS-туннеля. Наличие Docker-конфигурации не доказывает постоянный production.

**Предложено ассистентом, пока не реализовано и не утверждено отдельным ТЗ:**

1. Общая модель профиля, игровых сессий, облачных сохранений и проверяемых
   результатов при сохранении уже работающих игр.
2. Независимые игровые модули с одинаковым жизненным циклом запуска,
   сохранения, завершения и выдачи результата.
3. Общий сервис комнат, приглашений, подбора соперников и отключений;
   WebSocket для событий и ходов.
4. PostgreSQL для конкурентного изменения долговременных данных. Вынести
   расчёты ботов из транзакций записи. Выбор дополнительной очереди/Redis
   остаётся открытым; они не установлены в текущем проекте.
5. Постоянный HTTPS-сервер/домен, резервные копии, мониторинг, CI и
   автоматическое развёртывание.
6. Нагрузочные испытания ступенями 100 → 500 → 1000 одновременных игроков
   с измерением задержек, ошибок и восстановления. Это цели теста, не обещания.
7. Для будущих 2D-аркад можно отдельно рассмотреть Phaser. Текущие SVG/DOM
   оставить для игр, где они подходят. Phaser пока не добавлен; жанры будущих
   игр пользователь ещё не определил.

При следующей платформенной задаче сначала согласовать целевые сценарии,
одновременный онлайн и критерии готовности, затем делать один проверяемый слой.
Текущая просьба о памяти не является разрешением автоматически выполнить
миграцию базы, внедрить WebSocket или менять экономику.

Источники обсуждавшихся архитектурных ограничений и вариантов:
[SQLite](https://www.sqlite.org/whentouse.html),
[FastAPI WebSockets](https://fastapi.tiangolo.com/advanced/websockets/),
[Telegram Mini Apps](https://core.telegram.org/bots/webapps),
[Phaser](https://docs.phaser.io/phaser/getting-started/what-is-phaser).

## 13. Запуск и безопасное продолжение работы

Работать из Git root Развивайки, команды выполнять в PowerShell.

```powershell
# Текущее состояние; сначала проверить существующие процессы и свободный порт.
git status --short
git remote -v
git branch -vv
python run_local.py --status

# Обычный локальный запуск: API + временный HTTPS-туннель + бот.
python run_local.py

# Только API для локального просмотра; не запускать вторую копию на занятом 8080.
python -m uvicorn webapp.backend.main:app --host 127.0.0.1 --port 8080

# Функциональные проверки.
python -m unittest discover -s tests -p 'test_*.py' -v
node tests/puzzles.cjs

# Проверить только изменение и отправить в уже настроенный репозиторий.
git diff --check
# git add -- <явные пути текущей задачи>
# git commit -m '<содержательное описание>'
git push origin main
git ls-remote origin refs/heads/main
```

`TG_BOT_TOKEN`, `APP_URL`, пути БД и другие значения брать из приватного
окружения и `.env`, а не из этой памяти. Инструкция первичной настройки —
в README и `.env.example`. Никакие токены, содержимое initData, пароли,
ключи, guest-токены, приватные URL и сырые данные пользователей в память,
коммиты или ответы не копировать. Временный публичный адрес туннеля получать
из текущего runtime после проверки; не восстанавливать старый адрес из чата.

Локальный порт API — 8080. QA в предыдущей работе — отдельный 8081 с
`GAME_DB_PATH` и `POKER_DB_PATH`, направленными в отдельные тестовые БД.
В Docker API слушает внутренний 8001, Nginx публикует 8080. Не переносить
порты и команды соседних проектов в Развивайку.

Не останавливать бот/туннель ради изменения документации. При изменении API
может потребоваться контролируемый перезапуск только API через существующий
супервизор, с подтверждением результата. Постоянный production и работа
на телефоне должны проверяться отдельно от local preview.
